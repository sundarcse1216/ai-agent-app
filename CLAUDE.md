# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-agent AI assistant. A hybrid classifier routes each free-text query to one of six agents (weather, SQL, event recommendation, RAG document search, image generation, general chat). It runs three ways from the same `core/`/`agents/`/`database/` business logic: a console REPL (`main.py`), a scripted demo (`demo.py`), and a FastAPI web backend (`api/`) with a React frontend (`frontend/`) on top. See `README.md` for setup/run instructions and the "why these choices" rationale behind the web-layer design — this file is about how the code fits together, not how to run it.

## Tests

```bash
python -m pytest tests/ -v
```

Mocks `LLMService.chat`/`LLMProvider` and the `requests`/weather API boundary — no Ollama/network access needed. `TestSQLAgent`/`TestEventRepository` exercise real SQLite. `tests/test_semantic_router.py` mocks the embedding model with deterministic unit-circle vectors. `scripts/tune_classifier_threshold.py` is a standalone (not automated-suite) tool for empirically checking the classifier's confidence threshold against a labeled query set.

## Architecture

**Console request flow:** `main.py` → `Controller.process()` → `IntentClassifier.classify()` → `Router.route(intent, query, session)` → one `BaseAgent` subclass → `ResponseFormatter.success()`. **Web request flow:** same `Controller`-equivalent logic, but `api/routes/chat.py` calls the classifier/router directly (`Controller` itself is console-only — the web layer doesn't use it) and looks up a per-`X-Session-Id` `Session` from `api/session.py::SessionStore` instead of one process-lifetime session.

- **`core/intent_classifier.py`** — hybrid: `core/semantic_router.py` embeds the query (sentence-transformers, `BAAI/bge-small-en-v1.5`) and compares it against per-intent exemplar phrases in `core/intent_exemplars.py` via max cosine similarity (nearest single exemplar, not a centroid). Below `CONFIDENCE_THRESHOLD` (0.55), falls back to an LLM classification call. Not the original keyword-substring matcher — that's gone, but `tests/test_cases.py::TestIntentClassifier`'s cases (including two historical negative-case regressions) still assert on the same public `classify(query)` contract.
  - **Recurring misroute pattern, found repeatedly via live usage, not the test suite:** a phrasing that combines an intent's core verb with vocabulary another intent's exemplars are rich in (a place name, an event/celebration word) can lose to that other intent, because the exemplar set for the *correct* intent has no coverage of that combination. Concretely hit twice: self-introductions with a location ("I'm Sundar from Malaysia") lost to `recommendation`/`rag`/`weather` until `chat` got exemplars combining introductions with places; "generate image for singapore birthday" lost to `recommendation` until `image` got exemplars combining generation verbs with places/events. **The fix is always the same:** add a few natural (not literally-the-failing-phrase) exemplars to the correct intent covering that combination, then verify against *held-out* variants of the pattern (not the literal reported phrase) to confirm real generalization, via `scripts/tune_classifier_threshold.py` or a quick manual `SemanticRouter().classify()` script. If you're debugging a new misroute, check `top3` scores first (`SemanticRouter.classify()` returns them) — the margin between the correct and winning-wrong intent tells you whether it's a genuine gap (winning score much higher) or a coin-flip-close case.
- **`core/llm_provider.py`** / **`core/providers/`** — `LLMProvider` interface (`chat`, `chat_messages`, `stream`, `stream_messages`) with `OllamaProvider`/`OpenAIProvider` implementations, selected by `LLM_PROVIDER` via `core/llm_provider_factory.py` (cached singleton). `core/llm_service.py` is a thin backwards-compatible shim so `WeatherAgent`/`SQLAgent`/`RecommendationAgent` don't need to know a provider abstraction exists. `RAGAgent` picks its LangChain chat-model class (`ChatOllama`/`ChatOpenAI`) the same way, one layer down, since its retrieval chain needs a LangChain model object, not the raw `LLMProvider`.
  - `stream_messages` is deliberately **not** `@traceable` (LangSmith) in either provider — tracing that generator hung requests when consumed through this app's nested streaming call chain inside Starlette's `iterate_in_threadpool`. `chat_messages` (non-streaming) is traced fine. If you add LangSmith tracing elsewhere, test the *actual* streaming path through a live HTTP request before trusting it, not just a direct function call — this exact case looked fine in isolation and hung in practice.
- **`core/router.py`** — `Router.__init__` builds all six agents once (pooled — this is what makes constructing a `Router` expensive: RAG's embedding model + FAISS index load here). `Session.turns` is **one shared conversation history for the whole session**, regardless of which agent handled each turn — `Router.route()`/`route_stream()` call `core/conversation_context.py::record_turn()` after every turn, for every intent, and pass `session.turns` into any agent whose intent is in `CONTEXT_AWARE_INTENTS` (`chat`, `rag`, `weather`, `recommendation`). This was a deliberate fix, not the original design: an earlier version kept `chat_history`/`rag_history` as *separate* lists, which meant something said during a `rag`-routed turn was invisible to `ChatAgent` on the next turn (and vice versa) even though the user experiences it as one conversation. If you add a new context-aware agent, add its intent to `CONTEXT_AWARE_INTENTS` and have it read (not own) `turns` — **agents themselves hold no per-conversation state**, so one shared instance safely serves many concurrent sessions.
- **`agents/*.py`** — `BaseAgent.handle(query) -> str` is the base contract; context-aware agents take an additional `turns: list[dict]` parameter (`[{"query", "response", "agent"}, ...]`, oldest first) and just read it — they don't return an updated version, `Router` records the turn centrally. `ChatAgent`/`RAGAgent` also implement optional `handle_stream(query, turns)`, a generator yielding `{"type": "token"/"done", ...}` dicts (falls back via `NotImplementedError` for agents that don't implement it — weather/SQL/recommendation/image do one or more blocking calls with no meaningful partial output). Agents catch their own exceptions and return user-facing `"❌ ..."` strings rather than raising; the API layer derives `ChatResponse.is_error` from that prefix at the boundary rather than agents raising structured exceptions.
- **`agents/sql_agent.py`** — LLM generates SQL from the live schema, then `validate_sql()` blocks non-SELECT via keyword denylist + length cap before `execute_query()` runs it — the security boundary for this agent, don't weaken without equivalent protection. `generate_sql()` also truncates at the first semicolon, since LLMs sometimes append trailing prose after the query on the same line (`"SELECT ...; This returns..."`), which SQLite rejects as a second statement — found via live testing, not something the mocked tests would catch. Not context-aware (not in `CONTEXT_AWARE_INTENTS`) — SQL questions are typically self-contained; extend it the same way as weather/recommendation if that stops being true.
- **`agents/rag_agent.py`** — LangChain history-aware retrieval chain over a FAISS index (`documents/` → `vectorstore/faiss_index/`, built once, delete the directory to force a rebuild). `turns` gets converted to LangChain `HumanMessage`/`AIMessage` pairs (`_turns_to_messages`) right before each chain call. `handle_stream()`'s chunks: the chain's first 1-2 streamed items carry no `"answer"` key (input/context echo), only later ones do — verified empirically against the real chain before writing that code, not assumed.
- **`agents/recommendation_system.py`** — takes a `weather_agent` constructor argument (injected by `Router`, the same pooled instance used for the `"weather"` intent) rather than constructing its own. Follow this pattern for any future agent-to-agent dependency. Its LLM-based location/date extraction reads `turns` (via `core/conversation_context.py::format_recent_turns`) so a bare follow-up like "recommend an event" can recover a location mentioned in an earlier turn — including one handled by a different agent.
- **`agents/image_agent.py`** — OpenAI `gpt-image-1`, style-detection prompt engineering, retries with backoff. Not context-aware.
- **Caching:** `weather_cache`/`rag_cache` are module-level `cachetools.TTLCache`s built via `core/cache.py::make_cache()`. `rag_cache` is keyed purely by query text — two sessions with different prior `turns` asking the same question can share a cached answer regardless of that context; a known, accepted limitation, not a bug.
- **`logger.py`** — single shared logger (`"CapstoneLogger"`) → `outputs/logs/app.log`, daily rotation. `api/middleware.py` logs the HTTP layer through the same logger. Every layer logs at INFO: `core/providers/*.py` log each LLM call (request + response), `core/conversation_context.py::record_turn()` logs every agent's final response (one place, covers all six agents), and `api/routes/chat.py` logs the final API response including running session cost/tokens.

## Cost tracking (`core/cost_tracking.py`)

Per-session dollar-cost budget (`MAX_COST_PER_SESSION_USD`, default `$0.50`) — `Session.usage` (a `core.cost_tracking.Usage`) accumulates `prompt_tokens`/`completion_tokens`/`cost_usd` across a session's turns; `Router.route()`/`route_stream()` hard-block further LLM calls once `usage.over_budget()` is true, before even calling the agent.

**Two different propagation mechanisms are used, deliberately — this is the most non-obvious thing in this codebase, read this before touching cost tracking:**
- **Non-streaming calls** (`route()`, `LLMService.chat` → `chat_messages`): usage is recorded via a **contextvar** (`bind_usage()`/`record_usage()`), the same "ambient context" pattern OpenTelemetry/Sentry/LangSmith use, so `OllamaProvider`/`OpenAIProvider` (process-wide singletons) can record into the *correct* session without every agent method threading a `usage` parameter through. This is safe here because a plain synchronous call never crosses a thread-dispatch boundary partway through.
- **Streaming calls** (`route_stream()`, `stream_messages()`): usage is passed as an **explicit parameter** all the way from `Router` through `ChatAgent.handle_stream()`/`RAGAgent.handle_stream()` to the provider. This is not a style choice — I built the contextvar version first, and **directly tested it end-to-end and it silently recorded nothing.** Starlette's `iterate_in_threadpool` (which drives every SSE response) dispatches a *separate* thread-pool call per yielded token; a `ContextVar.set()` made in one dispatch does not survive into the next, because each dispatch re-copies context from the calling (event-loop) context, not the previous worker thread's mutated one. A generator's own local variables/parameters don't have this problem — they're part of the generator's frame state, restored on every resume regardless of thread. **If you add ambient-context-based tracking (cost, tracing, anything) to a code path that streams through this app's call chain, test it live through a real HTTP request before trusting it — a plain function-level test won't catch this, it only breaks once nested across `iterate_in_threadpool`'s per-token dispatches.**
- **RAGAgent** doesn't use `LLMProvider` at all (its chain calls a LangChain chat model directly), so neither mechanism above applies to it directly — instead `agents/rag_agent.py::_UsageCallback` hooks the chain's `on_llm_end` via LangChain's callback system, passed in explicitly via `config={"callbacks": [...]}` (same explicit-passing reasoning as the streaming case — a callback invoked from inside LangChain's own execution shouldn't rely on ambient context either). It reads `message.usage_metadata`, not `llm_output['token_usage']` — confirmed by testing that the latter is `None` for `ChatOllama` (`langchain_ollama` doesn't populate it) though it does exist for `ChatOpenAI`; `usage_metadata` is populated the same way for both. The chain fires `on_llm_end` **twice** per turn once there's prior history (once to reformulate the question standalone, once to generate the answer) — both fire the callback and both get summed, which is the genuinely-correct total, not double-counting.
- **`ImageAgent`** uses the ambient/contextvar mechanism (safe — it's always invoked via `route()`'s single dispatch, image generation never streams). `gpt-image-1` reports token usage on its response despite being an image endpoint (confirmed via the `openai` SDK's `ImagesResponse`/`Usage` types) — unlike older DALL-E-style endpoints, which don't.
- **Known gap:** the classifier's LLM fallback (`core/intent_classifier.py`, only fires below `CONFIDENCE_THRESHOLD`) runs *before* `Router.route()`/`route_stream()` are called, outside the scope where usage gets bound/passed either way — its cost isn't currently counted.
- Pricing table (`OPENAI_PRICING_PER_MILLION_TOKENS`) is a best-effort estimate that will drift — verify against platform.openai.com/pricing before trusting it for real budget decisions. Ollama is always `$0`.

## Web layer (`api/`)

- **`api/app.py`** — `create_app()`, lifespan hook builds `IntentClassifier`/`Router`/`SessionStore` once at startup (same pooled-resource lifecycle as the console app).
- **`api/session.py`** — `SessionStore`, a `TTLCache`-backed `session_id -> Session` map. Single-process, in-memory — a deliberate scope boundary (see README), not something to "fix" without also deciding on a shared store like Redis for multi-instance deployment.
- **`api/routes/chat.py`** — `POST /api/chat` (blocking) and `POST /api/chat/stream` (SSE: `intent` → zero-or-more `token` → one `result` event). Both mint a session id server-side if `X-Session-Id` is missing, echoing it back.
- **`api/routes/agents.py`**, **`api/routes/images.py`**, **`api/routes/health.py`** — agent display metadata (so the frontend doesn't hand-duplicate `ResponseFormatter.AGENT_NAMES`), generated-image serving (path-traversal-safe via `os.path.basename`), liveness/readiness.

## Data

- `database/company.db`, `database/events.db` — SQLite, seeded idempotently at startup by `database/setup_*_database.py`. `setup_events_database.py` upserts fixed ids 1-4 via `INSERT OR REPLACE` (not `OR IGNORE` without explicit ids) — the original `OR IGNORE`-without-ids version silently accumulated duplicate rows on every restart, since new autoincrement rowids never collide.
- `documents/` — RAG source files (HR policy docs + a sample PDF spec).
- `vectorstore/faiss_index/` — persisted FAISS index; not regenerated unless missing.

## Frontend (`frontend/`)

React + TypeScript + Vite. `src/hooks/useSession.ts` generates/persists the `X-Session-Id` UUID in `localStorage`. `src/api/chatStream.ts` is a hand-rolled SSE-over-POST parser (no library — browser `EventSource` doesn't support POST bodies). Weather/SQL/recommendation responses render as monospace text (the backend already formats them well — `tabulate` grids, emoji sections); chat/RAG render as markdown; image responses get a real `<img>` **and a download link** (`GeneratedImage.tsx` — deliberately does *not* show the agent's raw response text, since it contains a server-filesystem path that's meaningless, and a minor leak, to a browser user) via `ChatResponse.image_url` (parsed at the API boundary from the agent's success message, see `api/routes/chat.py::_extract_image_url` — if you change `ImageAgent`'s success-message format, update that regex too). `UsageIndicator.tsx` shows the running session cost/token total (`ChatResponse.session_cost_usd`/`session_tokens`, see the cost-tracking section above) above the input bar, with adaptive decimal precision since small OpenAI-mini-model costs round to a misleading `$0.0000` at a fixed 4 places.
